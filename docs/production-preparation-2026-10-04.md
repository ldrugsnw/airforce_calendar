# 운영 배포 전 보안·호환성·복구 준비

2026-10-04. 운영 DB 점검과 백업은 읽기 전용으로 수행했다. 원격 마이그레이션, 운영 기록 정정·삭제, 병합·배포는 실행하지 않았다. 보안·정정 변경은 로컬에서 검증했으며 PR #4에 커밋·push한다. **보안 수정도 아직 원격에 적용되지 않았다.**

## RPC 접근 보완

- `202609070001_rpc_privilege_lockdown.sql`: 입력 제한 처리와 독립적으로 내부 `app_snapshot`, `app_assert_active`, `app_validate_state`, Auth 트리거 함수의 PUBLIC/anon/authenticated 실행 권한을 회수한다. 가입 hook은 supabase_auth_admin만 실행할 수 있다. 기존 앱용 `api_*`의 authenticated 실행은 유지한다.
- `202610040004_rpc_access_hardening.sql`: `app_assert_owner`를 추가해 계정 인자가 현재 `auth.uid()`와 같은지 검사한다. 활성 계정 확인·일정 검증에도 동일 검사를 적용한다. 스냅샷은 소유권 조건으로 필터링해 잘못된 재권한 부여에도 다른 계정 데이터를 반환하지 않는다. 새 내부 함수의 소유자는 기존 SECURITY DEFINER RPC와 같은 postgres로 명시한다.
- 스냅샷의 새 계정 필드는 JSON으로 읽어 온보딩 컬럼이 없는 기존 운영 스키마에도 동작한다. 클라이언트는 기존 `api_get_app_snapshot()` 등을 그대로 사용한다. 본인 조회는 지원 API로 성공하며, 내부 함수 직접 호출은 본인도 지원하지 않는다.
- postgres가 앞으로 만드는 함수의 기본 PUBLIC/anon/authenticated 실행 권한을 제거하고, 지원하는 앱 API만 명시적으로 허용한다. PostgreSQL의 기본 PUBLIC EXECUTE는 스키마별 revoke만으로 제거되지 않아 전역 기본 권한도 회수한다. 기존 다른 함수는 변경하지 않지만, 이후 다른 스키마·확장의 새 함수에도 필요한 역할을 명시적으로 허용해야 한다.
- 관련 기존 `api_*`는 사용자 인자를 받지 않고 auth.uid()를 기준으로 동작하며, 갱신 대상 소유권을 검사한다. 계정 ID를 받는 내부 활성/일정 검사 함수의 정보 노출 경로도 닫았다. 현재 공개 가입 hook은 빈 객체를 반환하지만 불필요한 공개 권한을 제거했다.
- 선행 권한 회수만으로 외부 직접 호출 경로를 닫을 수 있다. 이후 온보딩 스냅샷 재정의는 기존 함수 ACL을 보존하고, 마지막 보완에서 소유권 필터를 다시 확정한다. 기존 적용 파일을 수정하거나 재실행하지 않는다.

## 위반 8건 보존과 소유자 정정

사용자는 기존 8건을 보존하고, 새 온보딩에서 직접 올바른 일수·획득일을 입력한 뒤 변경 범위를 확인해 저장하기로 결정했다. 운영 값·소유자 식별정보는 출력하거나 저장소에 복사하지 않았다.

| 위반 유형 | 건수 | 일정 연결 |
| --- | --- | --- |
| 일수 365일 초과만 해당 | 6 | 활성 사용 일정 없음 |
| 일수 초과 및 획득일 2999년 이후 | 2 | 활성 사용 일정 없음 |

중복 제외 8건이다. 획득일 2000년 이전, 사유·메모 길이, 사용/외출 날짜·사유의 위반 및 계정 행 누락은 없었다. 활성 일정이 없다는 이유로 테스트 기록이나 삭제 가능한 기록이라고 판단하지 않는다.

### 읽기와 저장 계약

- 서버 스냅샷은 기존의 양수 정수 일수와 실제 존재하는 범위 밖 획득일을 그대로 읽는다. 새 입력 검증은 1~365일·2000~2999년을 유지한다. 없는 날짜나 잘못된 형식을 허용하는 변경은 아니다.
- 서버 로딩이 성공한 미완료 계정은 가입 시점과 관계없이 소개부터 시작한다. 완료 계정이라도 범위 밖 기록이 있으면 정정 온보딩을 연다. 정상 완료 계정과 로컬 모드는 기존 동작을 유지한다.
- 기존 기록 이어 쓰기/새로 설정하기를 유지한다. 새로 설정하기는 일수 초안만 비우며 원본을 삭제하지 않는다. 연가·성과제 외의 종류도 범위 밖 기록이면 같은 ID의 정정 항목을 표시한다. 정상인 다른 종류는 그대로 둔다.
- 범위 밖 일수는 원본 그대로 표시한다. 범위 밖 획득일은 원본을 별도로 표시하고 날짜 입력은 비워 **유효한 날짜를 직접 입력하도록 요구**한다. 기존 날짜를 null로 대체하거나 자동으로 오늘/최댓값으로 바꾸지 않는다. 정상 날짜는 그대로 유지할 수 있다.
- 범위 밖 기록의 선택 해제는 막는다. 변경 확인 화면에 일수·획득일의 전후 값과 일정 보존 범위를 표시한다. 확인 취소·유효하지 않은 입력·실패는 완료로 처리하지 않는다.
- 확인 저장은 기존 ID·생성 시각·사유·메모와 활성/취소 일정 참조를 유지하고, 승인한 일수·획득일만 갱신한다. revision은 갱신되며 기존 사용·예정 일수보다 작게 줄일 수 없다. 사용 일정 날짜나 외출은 변경하지 않는다.
- `202610040005_legacy_leave_correction.sql`은 기존 plan RPC를 확장한다. 소유권·전체 검토 상태 충돌·명시적 확인·원자적 저장·request ID 재시도를 유지하고, 모든 종류의 기존 정정을 허용한다. 남은 범위 밖 기록이 하나라도 있으면 전체 저장을 롤백하고 완료를 거절한다. 임의 삭제·절삭·날짜 대체·새 항목 중복 생성은 없다.

### 미적용 입력 제한 파일을 조정한 이유

운영에서 아직 미적용인 `202609100001_feedback_input_limits.sql`의 일수·획득일 CHECK 두 개만 `NOT VALID`로 변경했다. 기존 8건을 정정 전에 보존하면서 적용하기 위해서다. 다른 CHECK는 집계상 위반이 없어 정상 검증한다. 이미 적용된 운영 파일은 수정하거나 재실행하지 않았다.

`NOT VALID`는 기존 행 전체 검사를 미루며 **새 INSERT 및 UPDATE에는 즉시 제한을 적용**한다. 범위 밖 기록의 메모만 갱신해도 두 제한을 모두 만족하지 않으면 거절되므로 온보딩에서 함께 정정한다. 조회·일정 참조는 보존한다. 모든 소유자 정정 후 읽기 전용 집계가 0임을 확인하고 별도 승인된 전진 마이그레이션으로 두 CHECK를 `VALIDATE CONSTRAINT`할 수 있다. 이번 배포 준비 단계에서는 검증 완료로 표시하지 않는다.

## 자동 검증과 사용자 확인의 구분

- 전체 앱 테스트: 20개 파일·161개 통과, 실제 DB 연동 4개는 일반 실행에서 생략. 이후 추가한 완료 계정의 날짜만 정정하는 서버 UI 회귀도 별도 실행으로 통과했다(최종 총 162개). 로컬 온보딩·기존 사용자·계정 격리 회귀를 포함한다.
- 빌드·린트 통과. 마지막 서버 UI 회귀 추가 후 TypeScript 검증을 포함한 빌드를 확인했다. 통과한 전체 테스트와 DB 연동은 불필요하게 반복하지 않았다.
- 실제 로컬 Supabase DB 계약: 5개 파일·85개 통과. 보안 22개, 기존 기록 정정 13개를 포함한다. 본인 API 조회, 다른 계정 차단, Auth hook/기존 CRUD 호환성, 확인 필수, 잘못된 날짜·정정 대상 삭제 거절, 부분 갱신 롤백, ID/메모/일정 보존 및 새 잘못된 입력 차단을 확인한다.
- 실제 앱 UI ↔ 로컬 Auth/Provider/RPC: 4개 시나리오 통과. 기존 최초 저장·수정·선택 해제·이전 회귀 외에 세 종류의 범위 밖 가상 기록을 재입력 → 전후 값 확인 → 취소 → 응답 유실/재시도 → 재조회 → 달력 → 새로고침 순으로 검증했다. ID·생성 시각·사유·메모·활성/취소 일정 참조 보존과 한 번의 revision 갱신을 확인했다. HTTP localhost:54321만 허용하고 DB는 로컬 54322임을 확인했다. 테스트용 계정만 정리했으며 사용자 검토 계정과 기존 기록은 유지했다.
- 네트워크·공개 포트 없는 별도 운영 백업 복원 DB에서 **누락 7개 마이그레이션 전체를 순서대로 적용**했다. 기존 휴가 원문 지문이 동일하며 기존 8건이 보존되고 두 CHECK가 미검증 상태인 것을 확인했다. 새 정정 계약 13개도 통과했다. 모두 한 트랜잭션 안에서 시험 후 롤백해 복원본을 보존했다. 앞선 기존 운영 스키마의 보안 22개·선행 권한 회수 호환성 검증도 통과했다.
- 자동 UI 검증은 jsdom이며 Safari 렌더링 검증과 구분한다. 사용자가 iPad Safari에서 승인한 것은 앞선 신규/기존 계정 온보딩 흐름이다. **이번 범위 밖 기록 정정 UI의 iPad 수동 확인은 아직 하지 않았다.**

## 백업과 별도 복원 검증

- 운영 DB를 읽기 전용으로 PostgreSQL 17.6 `pg_dump` 전체 custom archive로 확보했다. public뿐 아니라 auth, storage, supabase_migrations 및 다른 비시스템 스키마를 포함한다. 역할 정의·멤버십은 별도 `pg_dumpall --roles-only --no-role-passwords`로 보관했다.
- 백업은 저장소 밖 `/tmp/airforce-prod-backup-20261004T063759/`에 있다. 디렉터리 권한 700, 파일 권한 600. 원본 아카이브 SHA-256과 검증 결과는 같은 디렉터리의 `verification.json`에 보관한다. 비밀번호·연결 파일·백업·보조 스크립트는 Git에 포함하지 않는다.
- 원본 백업을 변경하지 않고 PostgreSQL 17.6의 별도 컨테이너에 전체 역할·스키마·데이터를 복원했다. 외부 네트워크와 공개 포트가 없는 환경이며 기존 개발 Supabase와 분리했다.
- 46개 비시스템 테이블 전부의 건수 및 정규화된 데이터 지문이 원격과 일치했다. 비교는 UTC·C 정렬을 사용하고 사용자 값이나 지문은 출력하지 않았다. 마이그레이션 이력, 컬럼·제약·인덱스, 앱 RPC 본문/권한, RLS·정책, Auth 트리거, 역할 능력 및 실효 멤버십도 일치했다.
- 관리형 역할의 권한 부여자 재현은 빈 일반 PostgreSQL에서 제한되어, **로컬 복원 실습에서만 멤버십 grantor를 restore_admin으로 매핑**했다. 실제 역할 능력·멤버십·옵션은 일치하지만 grantor 메타데이터까지 동일하다고 주장하지 않는다. 원래 grantor 정의는 원본 역할 백업에 남아 있다. DB 소유자는 원본에 맞춰 복원했다.
- Storage 객체 건수는 0이라 별도 파일 객체 복원은 필요하지 않았다. 역할 비밀번호, Supabase 서비스별 비밀값, Dashboard Auth/OAuth/SMTP 설정은 DB 아카이브만으로 복구되지 않는다. 해당 설정의 별도 보호된 보관과 관리형 플랫폼 복구 절차는 배포 전 추가 확인이 필요하다.
- 성공한 복원 환경은 후속 확인을 위해 유지했다. 시작 실패한 이 작업의 빈 컨테이너만 정리했으며 기존 사용자·개발 기록은 지우지 않았다.

이 백업은 현재 환경의 보호된 **임시 보관본**이다. `/tmp`와 복원용 tmpfs는 영구·외부 백업이 아니다. 배포 전에 암호화된 영구 보관 위치와 접근 권한·보존 정책을 결정하고 파일 해시를 검증해 옮겨야 한다. 자동 백업 목록은 비어 있고 PITR은 꺼져 있으므로 이를 대신하는 관리형 복구 지점은 아직 확보하지 않았다. 이번 실습은 로컬 DB 복원 검증이며 운영 프로젝트 복원·서비스 재구성 리허설과 구분한다.

## Auth·관리형 복구: 확인과 미확인

확인: 공개 Auth 설정에서 Google/이메일 사용, 가입 허용, 이메일 자동 확인 비활성 상태를 확인했다. Auth→계정 생성 트리거와 계정 누락 0건, 현재 RPC 권한 및 RLS를 실제 스키마와 대조했다. 백업 목록 API는 비어 있고 PITR은 비활성으로 응답했다. 로컬 전체 DB 복원 검증은 완료했다.

미확인: Dashboard Site URL·redirect allowlist·실제 Hook 연결, SMTP 전달·OAuth 비밀값/설정, 관리형 백업의 확보·보존·복원 가능 지점, 실제 프로젝트 복구 절차와 소요 시간, Supabase 서비스 전체 재구성은 검증하지 않았다. 빈 목록과 서비스 상태만으로 복구 가능한 관리형 백업이 있다고 주장하지 않는다. 암호화·영구 다운로드도 아직 사용자 작업이다.

## 최종 원격 적용 순서

읽기 전용 이력·실제 정의 점검 기준 운영 대상은 CLI의 `airforce-calendar-beta` 프로젝트이며 운영 사이트가 가리키는 동일 대상임을 확인했다. 연결 값·인증 정보는 여기에 싣지 않는다. 적용 직전 대상과 이력을 다시 대조하고 새 쓰기 이후의 최신 백업을 확보한다. 이번 커밋·push 승인은 원격 적용 승인이 아니다.

이미 적용된 `202608240001_server_foundation.sql`·`202609060001_open_beta_signup.sql`은 재실행하지 않는다. 아래 7개는 점검 당시 원격에 누락되어 있었고 이번에도 원격 적용하지 않았다.

| 순서 | 파일 | 영향 |

선행 누락 버전이 있으므로 적용 도구의 out-of-order 처리와 dry-run 목록을 검토한다. 이력 수정·삭제나 기존 파일 재실행으로 우회하지 않는다. 각 파일이 하나의 일괄 트랜잭션이라고 가정하지 말고 실패 지점의 이력/스키마를 확인한다. 새 앱 공개 전에 7개 모두 적용 완료하고 API 권한·기존 조회·새 입력 제한·정정·재시도를 별도 검증 계정으로 확인한다. 운영 기록을 테스트 fixture로 사용하지 않는다.

### 복구와 배포 전 남은 작업

원칙은 앱 롤백 시 확장 컬럼·새 ID/완료 정보와 보안 보완을 유지하는 것이다. 기존 CRUD 시그니처는 호환되지만 이전 앱의 엄격한 스냅샷 검증은 범위 밖 기록 조회를 거절할 수 있어, 기존 기록 보존용 읽기 수정이 포함된 버전으로 복귀해야 한다. 앱 롤백은 소유자가 이미 저장한 정정을 되돌리지 않는다.

- 함수/제약을 되돌릴 필요가 있으면 백업 정의를 검토해 별도 전진 마이그레이션을 만든다. 취약한 공개 내부 RPC 권한을 복구하지 않는다. 획득일 NOT NULL 복원은 새 null 기록이 있으면 실패하며 날짜를 채워 우회하지 않는다.
- 테이블/새 계정 컬럼을 drop하거나 DB reset하지 않는다. 완료 표시 복구는 백업과 적용 후 실제 완료 계정을 대조해 최신 상태를 덮어쓰지 않는다.
- 전체 DB 시점 복원은 이후 정상 쓰기를 잃을 수 있다. 별도 환경에 복원해 필요한 기록·참조를 검토한 뒤 승인된 복구를 실행한다. 관리형 역할 grantor·비밀값·Auth 설정 복구는 위 미확인 범위를 별도로 해결해야 한다.
