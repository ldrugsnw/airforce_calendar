## 현재 목적과 진입 기준

기존 테스터도 소개 → 보유 휴가 입력 → 저장 → 완료 → 달력 이동을 경험한다. 가입 시점, 기존 기록, 로컬 이전 완료 여부는 새 온보딩의 완료 증거로 사용하지 않는다.

- 서버 스냅샷 조회가 성공한 `ready` 상태에서 계정 `onboardingCompletedAt`이 null이면 소개부터 시작한다. 로딩·오류·오프라인 캐시에서는 쓰기 온보딩을 열지 않는다.
- 기존 서버 기록이나 이전 가능한 기기 기록이 있으면 소개의 시작 버튼 다음에 `기존 기록 이어 쓰기 / 새로 설정하기`를 표시한다. 이전 안내가 소개 화면보다 먼저 나타나지 않는다.
- `이어 쓰기`는 기존 일수를 채워 입력 단계로 진행한다. 기기 기록만 있다면 서버에 복사하고 입력을 표시한다. 이 경로에서는 기기 원본을 삭제하지 않는다. 유효한 v1~v3 기기 기록을 이전용 v3로 읽고 문자열 ID와 사용 참조를 UUID 계약에 맞게 변환한다.
- `새로 설정하기`는 입력칸만 비운다. 기존 서버 연가·성과제는 각각의 기존 ID에 새 일수를 입력한다. 같은 종류가 여러 건이면 각각 표시한다. 포상 등 다른 종류와 외출은 유지한다. 기기 기록만 있는 경우에는 그 원본을 보존하고 비어 있는 서버에 새 입력을 저장한다.
- 실제 새 온보딩 저장에 성공한 계정만 완료로 판단한다. 브라우저 로컬 온보딩 키는 서버 완료 판정에 쓰지 않는다. 새로고침·재로그인과 기기 변경에도 서버 완료 상태를 유지한다. 사용자가 바뀌면 Provider도 초기화한다.
- 이전 마이그레이션의 기존 사용자 자동 완료 backfill은 새 온보딩 완료로 인정하지 않는다. `202610040003`은 실제 저장의 ID 레지스트리가 없는 자동 완료 시각만 null로 바꾼다. 보유 휴가·사용 일정·외출은 삭제하지 않고, 이미 새 온보딩을 저장한 계정은 유지한다.
- 저장 전 초안은 메모리에만 있다. 저장 전 새로고침은 소개부터 다시 시작한다. 성공 후에는 요약과 수정 화면을 유지하며, `첫 휴가 계획하기`는 `/calendar`로 이동한다.
- 로컬 모드의 기존 소개·완료 상태와 동작은 유지한다.

## 기존 데이터에 미치는 영향과 확인

보유 휴가 한 건의 ID에 사용 일정이 연결된다. 휴가 삭제는 취소된 사용 이력도 cascade 삭제할 수 있다. 사용 중인 일정이 있으면 서버가 삭제를 막는다. 따라서 기존 기록을 종류별로 합치거나 지우고 새 항목을 만드는 방식은 사용하지 않는다.

기존 서버 기록에 입력하는 일수는 이미 사용·계획한 일수를 포함한 **기록별 총 일수**다. 사용·예정 일수는 그대로 차감되며, 그 합계보다 작은 입력을 막는다. 일수 변경은 기존 ID·생성 시각·획득일·사유·메모와 사용 참조를 유지한다.

기존 항목을 바꾸거나 선택 해제하면 저장 전 `기존 기록 변경 확인` 화면을 연다. 항목별 이전/새 일수, 삭제 대상, 함께 삭제할 취소 이력 수, 유지되는 일정·다른 휴가·외출 수를 보여준다. `입력으로 돌아가기`는 데이터를 변경하지 않는다. `변경 내용을 확인했고 저장합니다`를 눌러야 변경·삭제 요청을 보낸다. 사용·예정 일정이 있는 항목의 삭제는 확인 화면 이전에도 막는다.

## 서버 저장 계약

완전히 새로운 빈 계정의 최초 저장은 기존 `api_save_onboarding`을 사용한다. 기존 데이터·이전 완료 기록·온보딩 ID 레지스트리가 있는 계정의 검토와 재저장은 `api_save_onboarding_plan`을 사용한다.

새 RPC는 검토한 항목의 UUID와 일수, 전체 검토 상태, 명시적 확인 여부를 받는다. 현재 서버 상태와 검토 상태가 다르면 revision 충돌로 거절하므로, 확인 후 다른 기기에서 추가된 일정이나 취소 이력을 조용히 삭제하지 않는다. 기존 ID는 소유권을 확인하고, 새 종류만 서버 ID를 생성한다. 선택 해제 후에도 ID 레지스트리를 유지해 재선택·재시도 중 중복 생성하지 않는다.

기존 `api_mutate_app`의 입력·revision·일정 보호를 재사용한다. 모든 변경·삭제와 계정 완료 기록은 한 트랜잭션으로 저장하며, 중간 실패는 전체 롤백한다. UI는 제출 중 입력을 잠그고 중복 요청을 막는다. 응답 유실의 자동/수동 재시도는 동일 request ID를 사용하며, 실패하면 완료 화면을 표시하지 않는다. 서버 커밋 후 응답 두 개가 유실되는 경우도 실제 DB 연동에서 검증했다. 충돌 시에는 입력을 유지하고 최신 상태로 변경 범위를 다시 확인한다.

브라우저 캐시 쓰기 실패는 서버 저장 성공을 실패로 바꾸지 않는다. 기존 계정 이전 RPC의 `digest()` 검색 경로 오류는 PostgreSQL 내장 SHA-256 호출로 수정했다.

```bash
sudo iptables-legacy -A FORWARD \
  -i br-7063d178e561 -o br-7063d178e561 \
  -s 172.18.0.0/16 -d 172.18.0.0/16 \
  -m comment --comment airforce-calendar-pr4-local-bridge -j ACCEPT
```

되돌릴 때는 동일 인자에서 `-A`를 `-D`로 바꿔 이 규칙만 제거한다. 규칙은 호스트 런타임 상태이며 재부팅 후에는 현재 브리지·대역과 규칙 존재 여부를 다시 확인해야 한다.

### 적용 전 확인과 적용 후 확인

- 대상 프로젝트 식별자와 원격 마이그레이션 이력, 현재 함수 정의·권한, Auth Hook·가입 설정을 확인한다. 원격 작업 승인은 별도로 받는다. 이번 커밋·push 승인은 원격 DB 적용 승인이 아니다.
- 적용 전 복구 가능한 백업과 복원 방법을 확보한다. 특히 `user_accounts`의 `onboarding_completed_at`/`onboarding_grant_ids`(이미 존재하면), 함수 정의와 권한, 적용 이력을 보관한다. 6번의 완료 표시 해제는 원래 시각을 SQL 자체에 보관하지 않으므로 사전 백업이 필요하다.
- 3번의 제한에 맞지 않는 휴가 일수·획득일·사유·메모, 사용 일정 날짜, 외출 날짜·사유를 읽기 전용으로 점검한다. 위반이 있으면 적용을 멈추고 사용자 데이터 수정 범위를 별도로 검토한다. 임의 자르기·날짜 채우기·삭제는 하지 않는다.
- 신규 앱을 공개하기 전에 누락된 마이그레이션을 1→6 순서로 모두 적용한다. 4번만 적용한 중간 상태로 새 앱을 공개하면 기존 테스터 소개 조건이 최종 목적과 달라진다. 전체 파일이 하나의 트랜잭션으로 처리된다고 가정하지 말고, 실패 시 이력과 실제 스키마를 확인한 뒤 누락 지점부터 복구한다.
- 승인된 대상의 별도 검증 계정으로 신규 최초 저장·기존 기록 확인·일수 수정·선택 해제·일정 보존·달력·재로그인을 확인한다. 운영 사용자 기록을 테스트 fixture로 사용하지 않는다. 최종 RPC 권한은 authenticated에만 부여됐는지 확인한다.

### 복구 방안

기본 복구는 이전 앱 버전으로 되돌리고 확장 DB 스키마를 유지하는 것이다. 이전 앱은 추가 스냅샷 필드를 무시하며 기존 CRUD/RPC 시그니처는 유지된다. 다만 이후 사용자가 명시적으로 저장한 일수 변경·삭제는 앱 롤백으로 되돌아가지 않는다. 특히 휴가 삭제 시 cascade 삭제된 취소 이력은 데이터 백업 없이는 복구할 수 없다. 활성 일정이 있는 휴가 삭제는 계속 차단된다.

- 1번: 테이블을 drop하거나 DB reset하지 않는다. 이후 사용자 데이터가 생긴 서버 기반 스키마의 제거는 데이터 손실을 일으킨다. 복원이 꼭 필요하면 백업을 별도 환경에 복원해 변경분을 대조하고 승인된 복구 계획을 세운다.
- 2번: 가입 정책을 되돌려야 한다면 백업된 hook·트리거·권한과 Dashboard 설정을 함께 복원한다. 이후 가입한 사용자는 삭제하지 않는다. allowlist 복원은 신규 가입을 막을 수 있으므로 별도 정책 결정이 필요하다.
- 3번: 새 제한을 되돌려도 획득일 null 허용은 유지하는 편이 안전하다. 이전 NOT NULL 복원은 온보딩으로 저장한 null 행이 있으면 실패하며, 날짜를 임의로 채워서는 안 된다. 제약 변경은 백업된 정의에 근거한 별도 마이그레이션으로 처리한다.
- 4번: 완료/ID 컬럼과 확장 스냅샷을 유지한다. 컬럼 제거는 완료·재시도 식별 정보를 잃으므로 권장하지 않는다. RPC를 이전 정의로 복원하거나 사용을 중단하려면 새 앱의 쓰기를 먼저 중단한다.
- 5번: 지문 수정은 이전 시그니처와 호환되므로 유지한다. 원래 digest 검색 경로 오류가 있던 함수로 단순 복원하면 로컬 이전 장애가 재발할 수 있다.
- 6번: 기존 사용자 소개 정책만 되돌릴 때는 백업된 완료 표시를 검토해 복원한다. 적용 이후 실제 완료한 계정과 최신 기록을 덮어쓰지 않는다. 새 plan RPC는 이전 앱에서 호출하지 않으므로 그대로 남겨도 된다. 함수 제거가 필요하면 새 앱 호출을 먼저 중단한다.

각 파일의 역방향 마이그레이션은 제공하지 않는다. DB 전체 시점 복원은 그 이후 정상 쓰기를 잃을 수 있어, 별도 환경에서 복구하고 사용자별 변경분을 대조하는 절차가 필요하다. 마이그레이션 이력 행만 지우거나 기존 파일을 수정해 재적용하지 않는다. 필요한 복구는 별도의 검토된 전진 마이그레이션으로 처리한다.
